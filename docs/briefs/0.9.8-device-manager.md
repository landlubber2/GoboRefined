# Brief: 0.9.8 — Device Manager

Read `docs/briefs/COMMON.md` first and follow it. This is a **release** (`VERSION=0.9.8`; fix the number if
other releases were made in between).

## What the owner asked for (2026-11-16)

"Something as close as possible to the Windows Device Manager, with categories of devices, what driver a
device has and when a device doesn't have one, so users can easily identify it. If Linux has an online
driver base, perhaps a second tab with driver search or suggestions where to find them for your devices."

## Facts to build on (read before designing)

- **Linux has no online driver store like Windows Update.** Almost all drivers are part of the kernel and
  are already on the disk as modules; a device works when (1) the running kernel has a module that claims
  its ID, (2) that module is loaded and bound, and (3) the firmware file it asks for exists. So "no driver"
  on Linux is one of four different things, and the tool must tell them apart, in plain words:
  1. **Driver present and working** — a module is bound to the device.
  2. **Driver available but not active** — `modules.alias` of the running kernel has a match, yet nothing
     is bound (module not loaded, blacklisted, or its probe failed — the kernel log says why).
  3. **Driver active but firmware missing** — the kernel log has `firmware: failed to load …` /
     `Direct firmware load for … failed` / the SOF "firmware and/or topology file not found" message for
     that device.
  4. **No driver in this kernel** — no alias matches. Then the answer is a newer kernel, an out-of-tree
     driver, or nothing exists.
- Data sources that exist on the system or can be shipped in the image (pin and list any download):
  sysfs (`/sys/bus/pci/devices/*`, `/sys/bus/usb/devices/*`, each with `vendor`/`device`/`class`,
  `modalias`, and a `driver` link when bound), `lspci -k -nn`, `lsusb`, `/lib/modules/$(uname -r)/modules.alias`
  (`modprobe -R <modalias>` resolves a device to its module without loading it), `modinfo`, the name
  databases `pci.ids` and `usb.ids` (check their age on the image; ship current ones — both are freely
  redistributable), the kernel log (root only: use the existing `report` path of
  `spin/settings/gobo-settings-helper`), `/proc/asound/cards`, `/sys/class/net`, `/sys/class/bluetooth`,
  `/sys/class/drm`, `/sys/class/power_supply`, `/sys/class/input`.
- Online references that map a hardware ID to kernel support (verify each still exists and note its terms
  before linking; do not scrape or bundle their data unless the licence clearly allows it):
  - **linux-hardware.org** — a public database of hardware probes; device pages by ID show which drivers
    and kernel versions were seen working;
  - **LKDDb** (Linux Kernel Driver DataBase) — maps PCI/USB IDs to the kernel option and the kernel
    versions that contain a driver;
  - the kernel's own documentation and `linux-firmware` for firmware file names.
- The 0.8.6 brief (`0.8.6-unknown-hardware.md`) adds a small "Hardware check" list to Settings → About. If
  that exists when you start, this release **replaces and extends it**: one detection library, used by the
  About summary, by `gobo-report` and by the Device Manager. If it does not exist, build the library here
  and add the About summary yourself.
- The Settings app is Lua + GTK 3 through lgi (`spin/settings/`); a new program in the same style is the
  cheapest route. No polkit: anything needing root goes through the existing helper with strictly validated
  sub-commands.

## The program

A window "Device Manager" (`gobo-devices`): own entry in the app search and the dots menu, a button in
Settings → About, and reachable for administrators and standard users (read-only for standard users;
hidden for the Simple account kind if 0.9.1 exists).

### Tab 1 — Devices

- A tree like the Windows one, categories with icons, devices inside, collapsed by default except
  categories that contain a problem:
  Display adapters · Sound · Network (wired) · Wi-Fi · Bluetooth · Storage controllers and disks ·
  USB controllers · Input (keyboard, mouse, touchpad, touchscreen) · Cameras · Printers and scanners ·
  Battery and power · Sensors and system devices · Other / unknown.
  Derive the category from the PCI class and USB interface class, not from names.
- Each device row: a readable name (from `pci.ids`/`usb.ids`; fall back to the kernel's product string;
  never show a bare ID as the only label), and a state mark:
  **working** (green) · **driver not active** (yellow) · **firmware missing** (yellow) ·
  **no driver** (red) · **disabled** (grey, e.g. rfkill-blocked radios).
  Problem devices also get a badge on their category, and the window opens scrolled to the first problem.
- A summary line on top: "All devices have a driver" or "2 devices need attention".
- Selecting a device shows a details pane: vendor and model, hardware ID (`8086:9a49`, copyable), where it
  is connected (PCI slot / USB port, internal or external), **driver** (module name, its description and
  version from `modinfo`, "built into the kernel" when there is no module file), firmware files the driver
  uses and whether each is present, the last kernel messages mentioning this device (administrators only,
  through the helper), and for a problem a one-paragraph explanation in plain words of which of the four
  cases it is and what can be done.
- Actions (administrators, with the password prompt, each a validated helper sub-command taking only a
  device path that is re-checked against sysfs): "Try to start the driver" (`modprobe` the module that
  `modules.alias` names for this device — never a name typed by the user), "Rescan devices"
  (`udevadm trigger` / PCI rescan), "Unblock" for rfkill-blocked radios. No "uninstall driver", no
  blacklisting, no editing of module options in this release.
- "Copy details" and "Save report" (the same text `gobo-report` produces, with the device list on top).
- Updates itself when a device is plugged in or removed (poll sysfs every few seconds; remember that
  libudev events are unreliable on this system, see COMMON.md).

### Tab 2 — Find a driver

For every device in a problem state, one card with what the system can work out **offline first**:

- case 2 (driver available, not active): name the module, show the kernel's error line if there is one,
  offer "Try to start the driver";
- case 3 (firmware missing): name the exact file the kernel asked for and whether the shipped firmware
  collection contains it under another version; say that the next GoboRefined update is the way to get it,
  and offer "Save report" to send to the maintainer;
- case 4 (no driver in this kernel): say so plainly, show the kernel version, and consult a small table
  shipped in the image, `known-drivers.tsv` (hardware ID → what is known: "supported from kernel X.Y",
  "out-of-tree driver <name>, included in GoboRefined since <version>", "no Linux driver exists") — seed
  it with what this project already learned (Realtek 8852AU `2357:013f`/`0bda:1a2b`, the Intel SOF sound
  case, anything in `HANDOFF.md`), keep it easy to extend.

Then the **online** part, clearly separated and opt-in: per device, buttons "Look up this device on
linux-hardware.org" and "Look up in the kernel driver database", which open the web browser at the page
for that hardware ID (build the URL from vendor and device ID only; check the current URL scheme of each
site and keep it in one config file). Rules: nothing is sent automatically; no hardware probe is uploaded;
the only data leaving the computer is the ID in the URL the user chose to open, and the page says so in
one sentence. A search box "Search by hardware ID or name" does the same for any ID typed in (validate
it: hex IDs or plain words, no URL injection).

Do **not** download, compile or install drivers in this release. Out-of-tree drivers need kernel headers
and a compiler matched to the kernel, and installing them into a read-only A/B slot would not survive an
update; write into `docs/roadmap.md` what a later "driver add-ons on the data partition" feature would
take (module directory in the overlay, rebuild after each kernel update, signing), as an idea only.

## Quality bar

- Names a non-technical person understands; technical details one click away. No raw sysfs paths in the
  main view. Light and dark. Keyboard navigation in the tree. Opens in under two seconds on the VM.
- Never claims "working" when it only knows a driver is bound: for sound, network and Bluetooth add the
  functional check where cheap (a card is listed by ALSA, an interface exists, an adapter is powered) and
  word the state accordingly ("driver loaded, no sound card registered").
- The classification logic is a library with tests: fixtures captured from real machines as text files
  (the VM; the owner's desktop PC and ThinkPad — take them from the system reports in the lab notes or ask
  the owner to run a one-line capture command you provide), including the known cases: SOF firmware
  missing (0.8.3 laptop log), Wi-Fi adapter in "driver CD" mode, a USB device with no driver (in the VM:
  attach a virtual USB device whose class has no module, or fake a sysfs tree as `vm/net-test.sh` does),
  rfkill-blocked radio. A test script `vm/devices-test.sh` in the style of the other tests.
- Helper sub-commands: tests for refusals (wrong user kind, paths outside `/sys/bus/{pci,usb}/devices`,
  module names not derived from the device).

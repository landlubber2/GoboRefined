# Brief: 0.9.1 — accounts for everyone in the house, security hardening, current kernel

Read `docs/briefs/COMMON.md` first and follow it. This is a **release** (`VERSION=0.9.1`).

## What the owner asked for (translated from Polish)

"A normal user should not see root, only /home and the mounts; some security fixes; a current kernel. It
would be nice if the system were built so that you can create an account for a grandfather or a child and
have peace of mind, but also have the normal accounts for power users."

## Before starting (the launching session checks these with the owner)

Defaults below are used unless the owner answered otherwise under "Answers from the owner".

1. Should a Simple account be allowed to use USB sticks? Default: **yes** (read and write).
2. Should a Simple account have a web browser? Default: **yes**, no filtering.
3. Screen-time limits or web filtering for children? Default: **not in this release** (written to the
   roadmap as a later idea).
4. Firewall on by default (blocks incoming connections except when Remote access or Hotspot is switched
   on)? Default: **yes**.

### Answers from the owner

Owner started this brief on 2026-11-16 without changing anything: **all four defaults apply** (USB sticks yes,
web browser yes without filtering, no time limits or web filter in this release, firewall on by default).

## Part A — three kinds of accounts

Today Settings → Accounts knows "administrator" (group `sys`, may use `sudo`) and "standard". Add a third
kind and make the difference visible and reliable.

| Kind | For | May do |
|---|---|---|
| Administrator | the owner | everything, as today |
| Standard | a capable family member | own files, all programs, terminal; no `sudo`, no system settings |
| **Simple** | a child, a grandparent, a guest | own files and USB sticks, a short list of programs; nothing that can break the system or confuse |

Requirements for **Simple** (implement as a group, e.g. `simple`, that the look and tools check):

1. **File manager shows only what belongs to them.** PCManFM for a Simple user: starts in the home folder;
   side pane lists Home, Desktop, Documents, Downloads, Pictures, Music, Videos, USB drives, Trash and
   nothing else (no "File system", no bookmarks to system folders); the location bar and "go up" stop at
   the home folder and at `/Mount/Media/<stick>`; typing another path is refused with a friendly message.
   Do this with settings where they exist and a small LibFM/PCManFM patch where they do not (the patches
   live in `spin/patches/`, see how 0.6 added the USB place). The GTK file chooser (Open/Save dialogs in
   other programs) cannot be fully restricted — make it start in the home folder and hide the system
   mounts from its side pane (the long-standing "proc, sys, ESP…" clutter; fix that for everyone if you
   find the way), and say in the report what remains visible.
2. **Be honest about what this is**: hiding is for peace of mind, not the security boundary. The boundary is
   file permissions — see Part B item 1 (private home folders) — and no `sudo`.
3. **Menu and taskbar**: only chosen programs (default list: web browser, files, office, text editor,
   picture viewer, video player if present, calculator if present). No terminal, no Displays, no system
   tools, no "run command" (the app search only finds the allowed programs). The administrator edits the
   list per Simple user in Settings → Accounts (checkboxes over the installed applications).
4. **Shortcuts that open power tools are off** for Simple users (terminal on Win+Enter, Awesome restart,
   Lua prompt if any). Win+Escape, screenshots, clipboard history, desktops stay.
5. **Settings app** for Simple users: Appearance (light/dark, wallpaper), own password, Sound, About —
   nothing else is listed. Standard users: the same plus Network, Bluetooth, Displays, Trash. Check every
   page and every helper sub-command against the kind of the caller; the helper already refuses
   non-administrators for system changes — verify each sub-command, add tests.
6. **Power menu**: Lock, Log out, Restart, Shut down — as today.
7. **Larger text option** when creating a Simple account ("Larger text and icons": font and icon size up
   one step for that user) — only if cheap.
8. **Creating one is one dialog**: Settings → Accounts → Add a person → kind (Administrator / Standard /
   Simple, each with a one-line explanation) → name, login, password (a Simple account may have an empty
   password only together with "log in without password at the login screen" if LXDM supports that cleanly;
   otherwise require one). Changing the kind later works in both directions.
9. The installer keeps creating one Administrator; mention the other kinds on its closing screen.

Tests (extend `vm/settings-test.sh`; add `vm/accounts-test.sh` if clearer): create each kind, log in as
each, and assert: `sudo -n true` fails for Standard and Simple; a Simple user cannot list another home
folder, cannot open a terminal by menu, search or shortcut, sees only the allowed programs, PCManFM refuses
`/` and `/Programs`; the helper refuses every administrative sub-command for both; removing the account
removes its group membership and (if chosen) its home. `vm/input-test.sh` must stay green for an
Administrator session.

## Part B — security hardening (each item small; test that login, lock screen, sudo, su, updates still work)

1. **Private home folders**: mode 700 for new homes (AddUser path and installer) and fixed for existing
   ones at the first boot of this version (only `/Users/<login>` itself, never recursive; skip homes the
   owner deliberately opened is not detectable — just do it and say so in the README). Default `umask 027`
   or keep 022 with private homes — choose one, explain.
2. **Firewall**: iptables is on the image. Default policy: allow outgoing, allow established, allow
   loopback, drop incoming; open SSH only while Remote access is on; the hotspot rules keep working (they
   use their own chains). Loaded at boot by a boot script, rules in one readable file, a switch in
   Settings → Network ("Firewall: on/off", administrators only). IPv6 the same (`ip6tables` if present).
3. **Setuid audit**: list every setuid/setgid file in the image (`find / -xdev -perm /6000`); for each one
   we added (`gobonet_backend`, `udevil`, anything else) confirm it is needed and owned by root, not
   writable by others; write the list into `docs/security.md`.
4. **SSH**: keep root login disabled; add `PasswordAuthentication` left on (the owner uses it) but
   `MaxAuthTries 3`, `LoginGraceTime 30`, no empty passwords, only members of a group `remote` may log in
   (Settings → Remote access gets a list of who may connect; default: administrators).
5. **sudo**: confirm `secure_path`, `env_reset`, a 5-minute timestamp, and that our NOPASSWD lines allow
   exactly the listed commands with fixed arguments (re-check each with `sudo -l` as each kind of user).
6. **Passwords**: minimum length 8 for new passwords set through Settings and the installer (warn, with
   "use anyway" only for Simple accounts if the owner wants short ones — default: enforce 8 for
   administrators, 4 for Simple).
7. **Automatic login**: when switched on in Settings, show a plain warning that anyone who starts the
   computer gets into that account; never allow it for an Administrator without that confirmation.
8. **Kernel hardening sysctls** that do not break desktops: `kernel.dmesg_restrict=1` (already seen),
   `kernel.kptr_restrict=1`, `fs.protected_symlinks/hardlinks=1`, `net.ipv4.conf.all.rp_filter=1`,
   `kernel.yama.ptrace_scope=1` if Yama is built in. One file, loaded at boot.
9. **Web browser**: the Firefox on the image is from 2020. Replace it with the current Firefox ESR official
   Linux x86_64 tarball from mozilla.org (it needs glibc ≥ 2.17 and GTK 3.14: fine here) as a program under
   `/Programs/Firefox/<version>`, default browser, existing profiles keep working (ESR refuses to open a
   profile from a *newer* version only). Pin version and sha256. This is the most important security item
   for daily use. Also refresh the CA certificate bundle if the image has an old one (check its date).
10. Write `docs/security.md`: what the system protects against, what it does not (no disk encryption, no
    Secure Boot, no automatic security updates for bundled programs, hobby project), the account kinds, the
    firewall, how updates are signed. Short and honest; the README for publishing will link to it.

## Part C — current kernel

The image runs Linux 6.12.16 (an LTS series). Update to the **newest 6.12.y** release from kernel.org —
same series, so the configuration, the initramfs module and the out-of-tree Wi-Fi driver carry over. Do not
jump to a newer series in this release.

1. Find how the kernel on the image was built (GoboLinux recipe `Linux/6.12.16`, config in
   `/proc/config.gz`). Build the new point release with that config (`make olddefconfig`), as
   `/Programs/Linux/<version>` in the build environment, through a new step in `spin/build-programs.sh`
   with the source pinned in `build/sources.manifest`. Expect 1–2 hours of compile time on 2 CPUs: run it
   in the background, once.
2. Rebuild the out-of-tree `8852au` driver against it (existing step; mind `KERNELRELEASE`), regenerate the
   initramfs with the `goboab` dracut module, check `build-iso.sh` and `gobo-make-system` for hard-coded
   `6.12.16-Gobo` strings and make the kernel version a single variable.
3. Add CPU microcode (Intel and AMD, from linux-firmware/intel-ucode releases, licences recorded) as an
   early initramfs image if dracut on the image supports `--early-microcode`; otherwise write down why not.
4. The A/B update must carry the new kernel to existing installs (kernel and initramfs live in the slot;
   GRUB reads them from the slot): prove it in the update test — `uname -r` shows the new version after the
   update and the old one after `--rollback`.
5. The live ISO must boot with the new kernel in BIOS and UEFI.
If the kernel build fails twice for reasons you cannot fix in the time box, ship 0.9.1 without Part C and
say so; Parts A and B are worth a release on their own.

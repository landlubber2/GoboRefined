# Brief: 0.8.5 — works on machines we have never seen

Read `docs/briefs/COMMON.md` first and follow it. This is a **release** (`VERSION=0.8.5`).

## Why

Each new computer so far failed on a missing general piece (a graphics driver default, sound firmware), and
each time the owner had to send logs by hand. 0.8.4 added the firmware collection and driver defaults. This
release makes the remaining failures **survivable and self-explaining**: a stranger with unknown hardware
must always reach a desktop, and the system must be able to say what is wrong with it.

Read the "0.8.5" notes the 0.8.4 worker left in `docs/roadmap.md` and `HANDOFF.md` first (what it found
missing, which input drivers exist).

## Items, in priority order

1. **"Safe graphics" starts a desktop.** Today that boot entry adds `nomodeset` and X fails: the laptop log
   showed `modeset(G0): using drv /dev/dri/card0`, then "Screen 0 deleted because of no matching config
   section … Cannot run in framebuffer mode" — the kernel offers a simple framebuffer (`simpledrm`), but X
   treats it as a secondary GPU. Make the safe entry reach the login screen on any machine: an Xorg config
   used only in safe mode (selected by a kernel parameter such as `gobo.safe=1` read at boot, or by the
   boot scripts) that drives the firmware framebuffer through `modesetting` on simpledrm or through
   `fbdev`/`vesa`, with the compositor (picom) switched off and no display-layout restore. Test in the VM
   with `nomodeset` in BIOS and UEFI: login screen, login, desktop, Settings opens. The normal entries must
   not change behaviour.
2. **Automatic fallback.** If X fails to start twice in a row on a normal boot (the login screen never
   comes up), the next attempt uses the safe configuration by itself and the desktop shows a notice:
   "Started in safe graphics because the normal graphics driver failed — Settings → About → Hardware check".
   Keep it simple (a counter file written by the X wrapper `spin/ab/gobo-xorg`, cleared when a session
   starts). Must never loop and never trigger on a working machine; test by forcing a broken driver config.
3. **Hardware check** — Settings → About gets a "Hardware check" section, and `gobo-report` prints the same
   at the top of its file:
   - devices with no driver bound (PCI and USB: compare `lspci -k`/sysfs `driver` links), named in plain
     words with the device class ("Wi-Fi adapter: Intel … — no driver");
   - firmware the kernel asked for and did not get (kernel log lines `Direct firmware load for … failed`,
     `firmware … not found`, the SOF message), deduplicated;
   - graphics: which driver X uses, whether it is the safe fallback, whether 3D acceleration works;
   - sound: cards found or "no sound card found"; network: interfaces and their drivers; Bluetooth adapter;
     touchpad present and which input driver handles it;
   - a one-line verdict per area: OK / problem / not present, and at the end "Save system report" (exists).
   Reading the kernel log needs root: go through the existing root helper `report` sub-command, extended
   with a machine-readable section; no new privilege.
4. **Input devices**: if 0.8.4 found that the libinput Xorg driver is missing, build
   `libinput` + `xf86-input-libinput` only if they build with autotools here (newer libinput needs meson —
   then use the last autotools release, or keep `synaptics`/`evdev` and add sane touchpad defaults:
   tap-to-click, two-finger scroll, palm detection where the driver has it). A Settings page "Mouse and
   touchpad" (pointer speed, tap to click, natural scrolling, left-handed) applying per user at login.
5. **Display scaling**: detect a high-density panel (physical size from EDID against resolution) at first
   login and set a sensible `Xft.dpi` and cursor size; a slider in Settings → Appearance ("Size of text and
   interface": 100 / 125 / 150 / 200 %). Awesome bar, menus, GTK programs and the terminal font must all
   follow; test in the VM at 2560×1600.
6. **Laptop basics, each only if cheap**: battery icon shows charge and charging state correctly (check
   with a fake `power_supply` if the VM has none); brightness keys and volume keys work (acpid events or
   XF86 key bindings in `rc.lua`); closing the lid locks the screen (suspend is out of scope unless it
   works out of the box — test `echo mem > /sys/power/state` once in the VM and report).

## Delivery

As in COMMON.md ("Release delivery"). In `dist/README.md`: what to do when the screen stays black on a new
computer (choose "safe graphics"; the system now also falls back by itself), where the hardware check is,
and a request to send the system report for any machine where something is marked "problem".
